## Primary-source resource semantics

| Measurement or control | Established meaning and application |
| --- | --- |
| Frozen Python Budget | process_time measures user plus system CPU in the current process and does not include sleep. The current Windows build reports GetProcessTimes for that clock. It begins inside the consumer, so the external phase meter also covers initialization and verification. |
| Windows Job time limit | The Job Object kernel periodically enforces its configured user-mode CPU limit. With terminate-at-end-of-job and no notification-only action, it can stop the job independently of a worker check. This supplies user-mode enforcement. |
| Windows external combined CPU | GetProcessTimes returns separate user and kernel FILETIME counts in 100-nanosecond units. Job accounting provides aggregate user and kernel counts and job process counts. Their numeric representation does not establish pointwise accounting accuracy or a timer for the combined quantity. |
| Windows external elapsed time | GetTickCount64 supplies elapsed uptime including sleep or hibernation. Its resolution is limited by the system timer, typically 10–16 ms. Modern Windows relative handle waits omit time spent in low-power states, so the stop decision needs a fresh elapsed-clock sample, including after resume. |
| Windows termination and cleanup | TerminateJobObject applies process termination to all members. Cross-process termination is asynchronous, and pending I/O can delay exit. The process signal and a later zero active Job count are separate cleanup evidence. |
| Linux reference, unqualified here | Linux RLIMIT_CPU provides a process CPU limit in integer seconds and sends SIGKILL at the hard limit. It does not supervise elapsed time, give a separate aggregate descendant cap, establish accounting precision or guarantee complete reaping. User/system receipts would require native accounting under a qualifying host and a suspend-aware elapsed clock such as CLOCK_BOOTTIME plus independent cleanup. No Linux runtime or kernel enforcement was exercised here. |

## Selected recovery architecture

The only proposed policy is native Windows containment and user-mode termination, sampled combined CPU and elapsed watchdogs with early-stop margins, and fail-closed measured acceptance. A missing or exceeded measurement prevents acceptance. This policy explicitly does not enforce a strict instantaneous combined CPU cutoff or an exact elapsed kill deadline. It therefore needs separate Owner authorization to replace that admission requirement in a future contract. The scientific time and logical ceilings are kept as maximum acceptance numbers. No new supervisor launch entry, run, retry or implementation authorization is created. [Proposed Windows contract](WINDOWS_RECOVERY_CONTRACT.md) · [Proposed values](PROPOSAL.json)

No synthetic process probe was used. The recovery task needed a bounded facility inventory and a reviewable fallback specification. Running a termination experiment against an unimplemented policy would not qualify that policy or supply a worst-case latency bound. The two preserved source snippets are the exact read-only inventory code. They queried status or resolved exports without opening Job objects or spawning a scientific worker.
